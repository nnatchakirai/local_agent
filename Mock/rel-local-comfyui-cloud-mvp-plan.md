# Re:Local ComfyUI Cloud 개인화 관광 영상 MVP 계획

> 목적: 기존 관광지 추천 결과를 바탕으로 이용자가 5개 추천 장소 중 하나를 선택해 약 10초 분량의 개인화 영상을 보고, 목록으로 돌아와 다른 장소의 영상을 이어 볼 수 있는 최소 제품을 정의한다.
>
> 상태: 구현 전 제안 문서. 성능, 클라우드 워크플로 및 기존 API 계약은 실제 환경에서 검증해야 한다.

## 1. 근거와 구분 원칙

### 핸드오프 대화에서 확인한 사실

- Re:Local 김해 관광지 추천 및 실감형 전시 프로젝트 맥락이다.
- 코드 기반 로직이 관광지 후보 20개를 만들고, 그중 5개를 선택한다.
- 장소별로 준비된 해당 장소의 LoRA를 사용해 배경 이미지를 생성한다.
- 사용자가 준비해 로드한 `character.png`가 영상의 주인공이다.
- ComfyUI Cloud로 이미지 생성 후 이미지 기반 영상을 만든다.
- 영상 목표 길이는 약 10초이며, 생성 소요 목표는 선택 장소당 60초 이내다.
- 화면에는 추천 장소 후보가 보이고, 사용자는 각 장소 영상을 선택해 본 뒤 목록으로 돌아가 다른 장소를 선택할 수 있어야 한다.
- 기존/제안 API 이름으로 `GET /current_region`, `POST /api/survey`, `GET /api/video-status/{task_id}`가 언급되었다.

### 이번 문서에서 새로 제안하는 결정

- 아래의 세부 요청/응답 JSON, 상태값, 저장·캐시 키, 작업 큐, 폴백 동작, 제한값, 인수 기준 및 단계별 계획은 구현을 위한 제안이다. 기존 구현의 동작으로 간주하지 않는다.
- 60초 목표는 제품 목표이며 성능 보장이 아니다. ComfyUI Cloud 실행 환경, 모델/LoRA 준비 상태, 대기열, 영상 모델과 프레임 설정을 측정해 실현 가능성을 확인해야 한다.
- `PROJECT_CONTEXT.md`를 지정 경로(`/mnt/data/PROJECT_CONTEXT.md`)에서 찾을 수 없었고 작업 폴더에서도 발견하지 못했다. 따라서 파일에만 있었을 수 있는 기존 스키마, 인프라, 선정 로직 상세는 검증하지 못했다. 통합 전에 실제 코드와 계약 문서를 대조해야 한다.

## 2. MVP 범위

### 사용자 가치

사용자가 설문 또는 기존 추천 흐름을 완료하면 김해 관광지 5곳을 카드로 확인하고, 원하는 카드를 골라 자신의 캐릭터가 해당 장소를 배경으로 움직이는 짧은 영상을 재생한다. 재생을 마치거나 중단한 뒤 목록으로 돌아와 다른 장소도 볼 수 있다.

### MVP 포함

- 기존 추천 로직에서 최대 20개 후보를 수신하고 기존 규칙으로 상위 5개를 정한다.
- 선택된 5개 장소의 카드 목록 표시.
- 장소별 독립적인 영상 생성 요청, 진행 상태 표시, 재생 및 목록 복귀.
- 장소에 연결된 LoRA로 배경 이미지 생성.
- 준비된 `character.png`를 주인공으로 합성/조건화하여 영상 생성.
- ComfyUI Cloud 작업 제출 및 완료 산출물 전달.
- 재사용 가능한 결과 캐시, 실패 상태/재시도, 정적 이미지 폴백.

### 초기 범위에서 제외(제안)

- 이용자 간 공유·공개 갤러리, 다중 캐릭터 편집, 실시간 인터랙티브 영상.
- 장소를 사용자가 직접 검색·추가하거나 5개 추천 결과를 편집하는 기능.
- 생성 결과에 대한 복잡한 편집기, 장면 이어 붙이기, 음성·자막 생성.
- 무제한 동시 생성. 큐와 동시성 제한을 둔다.

## 3. 핵심 사용자 흐름

1. 프론트엔드는 기존 `GET /current_region` 계약을 호출해 현재 지역 정보를 읽는다.
2. 사용자는 현재 설문 흐름을 완료한다. 프론트엔드는 기존 제안 경로인 `POST /api/survey`를 호출한다.
3. 백엔드는 설문 결과와 사용자/세션 문맥을 이용해 후보 20개를 확보하고 5개를 선정한다. 응답에는 5개 장소 카드에 필요한 표시 정보와 안정적인 `recommendation_id`를 포함한다.
4. 프론트엔드는 5개 카드를 리스트로 표시한다. 각 카드는 장소명, 대표 이미지, 한 줄 설명, 영상 생성/준비 상태, 재생 버튼을 갖는다.
5. 사용자가 한 카드를 고른다. 준비된 영상이 있으면 재사용한다. 없으면 해당 장소 영상 작업을 생성하거나 기존 진행 중 작업을 반환한다.
6. 생성 중에는 카드/상세 화면에서 진행 상태를 보여준다. 사용자가 상세 화면을 떠나도 서버 작업은 계속되며, 목록에서 다시 들어오면 상태를 재조회한다.
7. 완료되면 약 10초 영상을 재생한다. 영상 종료 또는 뒤로 가기를 선택하면 5개 카드 목록으로 복귀한다.
8. 다른 카드를 선택해 같은 과정을 반복한다. 이미 완료된 영상은 캐시에서 즉시 재생한다.
9. 생성 실패 시 재시도 가능 여부와 정적 장소 이미지/설명 폴백을 표시한다.

### 화면 상태 제안

- **추천 목록**: 5개 카드. 각 카드별 `대기`, `생성 중`, `완료`, `실패`를 개별 표시.
- **영상 상세**: 장소명, 생성 상태 또는 재생기, 목록으로 돌아가기.
- **생성 중**: 불확실한 퍼센트를 꾸며내지 않는다. 실제 단계(`배경 생성`, `영상 생성`, `저장`)와 마지막 확인 시각을 제공한다.
- **완료**: 재생, 다시 보기, 목록 복귀.
- **실패/폴백**: 오류 안내, 재시도, 정적 대표 이미지 보기, 목록 복귀.

## 4. 권장 시스템 구성 및 파이프라인

```text
Frontend
  ├─ GET /current_region (기존 계약)
  ├─ POST /api/survey (기존 제안 경로)
  ├─ 장소 선택 → POST /api/videos (신규 제안)
  └─ GET /api/video-status/{task_id} (기존 제안 경로)
          ↓
Backend API ── Recommendation adapter (20 후보 → 5 장소)
          ↓
Task store / queue ── idempotency + concurrency limit
          ↓
Media orchestrator
  1. 입력/정책 검증, 장소·LoRA 매핑 확인
  2. 배경 프롬프트 및 영상 프롬프트 구성
  3. ComfyUI Cloud 이미지 워크플로 실행 (장소 LoRA)
  4. 생성 이미지와 character.png로 이미지-비디오 워크플로 실행
  5. 출력 검증(길이·코덱·크기·정책), 객체 저장소에 저장
  6. task 결과 갱신 → 프론트엔드 폴링 응답
```

### 워크플로 단계와 입력

| 단계 | 입력 | 출력/검증 |
|---|---|---|
| 추천 고정 | 후보 20개, 설문/지역 정보 | 5개 장소, 순위·선정 근거, `recommendation_id` |
| 설정 조회 | 장소 ID, LoRA 레지스트리, 프롬프트 템플릿 버전 | 장소별 LoRA 식별자/버전, 유효성 확인 |
| 배경 이미지 생성 | 장소 특성, 장소 LoRA, 모델·시드·생성 설정 | 배경 이미지 URI와 메타데이터 |
| 캐릭터 준비 | 신뢰된 `character.png`, 배경 이미지, 합성/조건 설정 | 캐릭터가 포함된 영상 입력 이미지 또는 조건 |
| 이미지-비디오 | 입력 이미지, 영상 모델/워크플로 버전, 약 10초 설정 | 영상 파일, 실제 길이·해상도·코덱 |
| 퍼블리시 | 검증된 미디어 | 재생 가능한 보호 URL, 만료/접근 정책 |
| 완료 처리 | 단계 결과 및 오류 | 최종 task 상태, 결과 URI, 기간, 재사용 가능 여부 |

**중요한 설계 확인:** “캐릭터가 주인공”이 LoRA 생성 이미지에 단순 오버레이되는 것인지, 참조 이미지/ID 조건을 영상 모델에 전달하는 것인지에 따라 노드와 품질이 크게 달라진다. 현재 워크플로에서 `character.png`를 어떻게 참조하고 인물 정체성을 유지하는지 먼저 확인한다. 투명 배경 PNG라면 알파 채널, 크기, 색공간도 검증한다.

## 5. API 호환 제안

기존 세 경로의 이름만 전달받았고 실제 요청/응답 스키마는 전달받지 못했다. 아래는 **신규 제안 계약**이며, 통합 시 기존 코드의 필드명·응답 래퍼·인증 규칙을 보존하는 어댑터를 둔다. `GET /current_region`은 기존 응답을 그대로 유지한다. 기존 응답 전체를 알지 못하므로 필드명을 임의로 확정하지 않는다.

### `GET /current_region` — 기존 계약 유지

- 기존 구현의 경로, HTTP 상태, JSON 구조, 지역 식별자 의미를 그대로 유지한다.
- 추천 요청에는 기존 응답 중 지역 식별/표시 정보를 백엔드 어댑터가 사용한다.
- 계약 변경이 필요하다면 별도 버전 또는 하위 호환 필드 추가로 처리한다.

### `POST /api/survey` — 기존 제안 경로와 호환

현재 설문 API가 추천 결과도 반환하는지 확인한 뒤, 해당 계약을 확장하거나 별도 추천 세션 생성 계약을 둔다. 아래는 이상적인 신규 응답 예시다.

```json
{
  "recommendation_id": "rec_...",
  "region": { "id": "...", "name": "김해" },
  "places": [
    {
      "place_id": "...",
      "name": "...",
      "rank": 1,
      "summary": "...",
      "thumbnail_url": "...",
      "video_status": "not_requested"
    }
  ]
}
```

- `places`는 5개(후보가 부족한 경우 그보다 적을 수 있음)를 반환한다.
- 설문 원문 개인정보는 필요한 최소 범위만 저장한다. 추천 결과는 식별 가능한 세션/사용자에 귀속한다.
- 백엔드의 후보 20개 선정 결과를 감사 가능한 내부 메타데이터로 남긴다. 전체 내부 점수 노출은 제품 정책에 따라 결정한다.

### `POST /api/videos` — 신규 제안: 장소 영상 요청

```http
POST /api/videos
Idempotency-Key: <client-generated-key>
Content-Type: application/json
```

```json
{
  "recommendation_id": "rec_...",
  "place_id": "...",
  "character_asset_id": "character_default_v1"
}
```

```json
{
  "task_id": "task_...",
  "status": "queued",
  "place_id": "...",
  "reused": false,
  "status_url": "/api/video-status/task_..."
}
```

- 장소가 해당 추천 세션의 5개에 속하는지 서버에서 검증한다.
- 동일 세션·장소·캐릭터·워크플로 버전 요청이 진행 중이면 기존 `task_id`를 반환한다.
- 캐시 완료 상태면 `status: "succeeded"`, `reused: true`, 결과 링크를 반환할 수 있다.
- 같은 idempotency 키의 재전송은 같은 작업을 반환한다.

### `GET /api/video-status/{task_id}` — 기존 제안 경로 보완

```json
{
  "task_id": "task_...",
  "status": "running",
  "stage": "video_generation",
  "created_at": "2026-10-27T00:00:00Z",
  "updated_at": "2026-10-27T00:00:12Z",
  "result": null,
  "error": null
}
```

완료 예시:

```json
{
  "task_id": "task_...",
  "status": "succeeded",
  "stage": "completed",
  "result": {
    "video_url": "https://...signed...",
    "thumbnail_url": "https://...signed...",
    "duration_seconds": 10.0,
    "expires_at": "2026-10-27T01:00:00Z"
  },
  "error": null
}
```

상태 조회는 세션/사용자 소유권 검증을 수행한다. 작업이 없거나 권한이 없는 경우 리소스 존재 여부가 노출되지 않도록 일관된 응답 정책을 사용한다.

## 6. 상태 모델 및 폴링

### 상태 제안

- `queued`: 제출됨, 워커 대기 중
- `validating`: 입력·장소·자산 확인
- `background_generation`: 장소 LoRA로 배경 생성
- `video_generation`: 이미지-비디오 변환
- `publishing`: 결과 검사 및 저장
- `succeeded`: 재생 가능
- `failed`: 자동 복구 불가 오류
- `cancelled`: 사용자가 취소했거나 시스템이 만료 처리

실패 재시도는 내부 `attempt`와 `retryable`로 기록하되 외부 상태를 불필요하게 세분화하지 않는다. `failed` 응답에는 기계용 안정 오류 코드와 사용자에게 안전한 설명을 분리한다.

### 폴링 제안

- 상세 화면이 활성화된 동안 2초 간격으로 시작하고, 장시간이면 3~5초로 늘리는 지수형 간격(최대 5초)을 적용한다.
- 완료/실패/취소 시 폴링을 중지한다. 앱이 백그라운드이면 중지하고 복귀할 때 한 번 재조회한다.
- `Retry-After` 또는 서버 권고 간격을 존중한다. 429/5xx에는 백오프와 지터를 적용한다.
- MVP는 폴링으로 시작한다. 동시 이용/트래픽이 커지면 SSE/WebSocket/푸시를 검토한다.

## 7. 캐싱 및 재사용

- 캐시 키에는 추천 세션/이용자 범위, `place_id`, 캐릭터 자산 버전 또는 해시, LoRA ID·버전, 이미지 모델/설정, 영상 워크플로 버전, 프롬프트 템플릿 버전을 포함한다.
- 우선 캐시 정책: 동일 이용자/세션 안에서만 결과 재사용. 공유 캐시는 동의, 라이선스, 개인정보, 생성물 권리 및 노출 정책 검토 후 별도 결정한다.
- 진행 중 중복 요청은 합쳐 하나의 작업으로 처리한다. 동일 요청의 재시도는 멱등성을 보장한다.
- 결과 파일은 공개 버킷에 두지 않고, 짧은 수명의 서명 URL 또는 인증 프록시로 전달한다.
- 캐시 TTL, 산출물 보존기간, 삭제 요청 처리 방식은 운영·법무 검토 후 확정한다.

## 8. 실패 처리와 폴백

| 실패 지점 | 재시도/복구 | 사용자 경험 |
|---|---|---|
| 장소에 LoRA 매핑 없음/비활성 | 자동 재시도하지 않음. 설정 오류로 격리 | 해당 장소 영상 불가 안내, 정적 장소 사진/설명 표시 |
| ComfyUI 제출 실패/일시 오류 | 제한된 횟수와 지수 백오프 | 생성 중 유지, 지연 안내 |
| 이미지 생성 실패 | 일시 오류만 재시도. 검증된 장소 대표 이미지 사용 여부는 정책 설정 | 영상 생성 실패 시 정적 이미지 폴백 제공 |
| 영상 생성 실패/시간 초과 | 재시도 가능 오류만 제한 재시도 | 재시도 버튼 제공, 정적 폴백 유지 |
| 결과 길이·형식 검증 실패 | 결과 폐기/격리, 필요하면 새 작업 재시도 | 실패 안내, 문제 결과는 재생하지 않음 |
| URL 만료/재생 오류 | 인증된 URL 재발급 후 1회 재시도 | 재생 재시도 후 목록 복귀 선택 제공 |
| 서비스 과부하 | 큐/동시성 제한, 빠른 429/503 또는 queued 정책 | 대기 예상이 불확실하면 수치 약속 없이 대기 표시 |

폴백은 “동영상 생성 완료”로 표시하지 않는다. 정적 이미지와 장소 설명을 보여주고 상태를 명확히 구분한다.

## 9. 지연 목표와 검증 계획

요구 목표는 **사용자가 장소 하나를 선택한 시점부터 재생 가능한 약 10초 영상을 받을 때까지 60초 이내**다. 이는 미검증 목표다. ComfyUI Cloud의 작업 대기시간, 실제 노드 워크플로 속도, 모델 콜드 스타트, 파일 이동·인코딩·검증, 네트워크 지연을 현재 정보만으로 예측할 수 없다.

### 측정 구간

- API 수락 및 큐 대기
- 배경 이미지 생성
- 캐릭터 조건/합성
- 이미지-비디오 추론
- 저장·검증·URL 발급
- 전체 사용자 체감 시간

### 초기 성능 예산(가설, 확정 SLA 아님)

| 구간 | 목표 예산(가설) |
|---|---:|
| API 검증·큐 등록 | 2초 |
| 큐 대기 | 8초 |
| 배경 이미지 생성 | 15초 |
| 영상 생성 | 25초 |
| 검증·저장·전달 준비 | 8초 |
| 합계 | 58초 |

이 수치는 측정 전의 계획 배분이다. 운영 전 실제 환경에서 충분한 표본을 수집해 p50/p90/p95, 실패율, 재시도 비율을 산출한다. 평균만으로 60초 달성을 선언하지 않는다. 목표를 못 맞추면 단계 병렬화 가능성, 사전 워밍업, 해상도/프레임/스텝, 모델 선택, 큐 동시성, 미리 생성할 수 있는 산출물 여부를 측정 기반으로 조정한다. 영상 품질 저하와 비용 증가를 함께 기록한다.

## 10. 데이터 계약 및 엔티티 제안

### 핵심 엔티

- `RecommendationSession`: `recommendation_id`, 주체(사용자 또는 익명 세션), 지역, 설문 참조/최소 파생 정보, 생성 시각, 만료
- `RecommendedPlace`: 세션 ID, `place_id`, 순위, 카드 정보, 후보/선정 메타데이터
- `CharacterAsset`: 자산 ID, 소유/사용 범위, 버전 또는 해시, 저장 위치, MIME, 크기, 검증 상태
- `PlaceLoraMapping`: `place_id`, LoRA 참조·버전, 활성 여부, 허용된 프롬프트 설정
- `VideoTask`: task ID, 주체/세션, 장소, 캐릭터, 워크플로 버전, 상태·단계, 재시도 횟수, 생성/완료 시각, 오류 코드, 결과 메타데이터, 멱등성 키 해시
- `MediaArtifact`: 유형(배경/영상/썸네일), 비공개 저장 키, MIME, 크기, 체크섬, 길이, 보존 만료

### 계약 원칙

- 내부 데이터베이스 필드와 공개 API 필드를 분리한다.
- 모든 시간은 ISO 8601 UTC로 전달한다.
- 안정 식별자를 사용하고, 장소명만으로 키를 만들지 않는다.
- 진행률 수치는 실제 측정 가능한 경우에만 제공한다.
- 오류 응답에는 `code`, 안전한 `message`, `retryable`을 제공한다. 내부 프롬프트/클라우드 자격증명/스택 추적은 노출하지 않는다.
- 프론트엔드에 LoRA 경로, ComfyUI 워크플로 내부 노드, 저장소 비공개 키를 보내지 않는다.

## 11. 보안·개인정보·운영

- `character.png` 업로드/사전 로드는 허용된 형식(PNG 등), 크기, 해상도, 디코딩, 악성 파일을 서버 측에서 검증한다. 원본 파일명은 저장 키로 사용하지 않는다.
- 자산과 영상은 기본 비공개이며 주체별 접근 제어, 짧은 만료 URL, 보존 만료 및 삭제 절차를 둔다.
- ComfyUI Cloud 자격증명은 백엔드 비밀 저장소에만 둔다. 브라우저에 노출하지 않고 로그에도 남기지 않는다.
- 사용자 입력 설문은 프롬프트에 직접 삽입하지 않고 검증/정규화하며 프롬프트 인젝션 및 금지 콘텐츠 정책을 적용한다.
- LoRA 파일/버전은 승인된 카탈로그에서만 선택한다. 임의 경로/모델 로드를 막는다.
- 요청별 인증·권한, 생성 빈도/동시성 제한, 비용 상한, 큐 적체 보호를 적용한다.
- 로그에는 task ID, 단계, 지연, 결과 코드 및 버전만 최소 기록한다. 원본 설문/이미지/서명 URL/비밀 값을 기본 로그에 기록하지 않는다.
- 관측 지표: 단계별 지연 분포, 60초 내 완료 비율, 성공·실패율, 큐 길이, 재시도, 캐시 적중률, 비용/영상, 재생 실패율.
- 운영 대시보드와 알림은 큐 정체, 실패 급증, 모델/LoRA 누락, 저장 실패, 예산 초과를 추적한다.
- 생성물 사용 동의, 캐릭터 이미지의 권리, 이용자 연령/민감 정보, 보존·삭제 정책은 출시 전 담당자 확인이 필요하다.

## 12. 인수 기준 제안

1. 설문 완료 후 기존 추천 로직에서 후보 20개를 입력으로 받아 최대 5개의 장소가 응답되며 카드에 필요한 필드가 채워진다.
2. `GET /current_region`의 기존 응답 계약과 이를 쓰는 기존 클라이언트가 변경 없이 동작한다.
3. 5개 카드가 보이고 각 카드는 다른 카드의 상태와 독립적으로 선택·생성·재생된다.
4. 한 영상의 재생을 마치거나 목록 복귀를 누르면 추천 목록으로 돌아가 다른 장소를 선택할 수 있다.
5. 선택한 장소 ID가 해당 추천 세션에 속하는지 서버가 확인하고, 그 장소에 매핑된 LoRA를 사용한다.
6. 파이프라인이 `character.png`를 주인공으로 사용하며 결과 영상의 실제 길이·형식을 검사한다. 약 10초 허용 오차는 제품·모델 설정과 함께 확정한다.
7. 완료 영상은 새로고침/재방문 후에도 정책상 유효 기간 동안 상태 조회와 재생이 가능하다.
8. 중복 클릭/네트워크 재시도로 동일 요청의 중복 비용 작업이 발생하지 않는다.
9. 재시도 가능한 오류와 불가능한 오류가 구분되고, 실패 때 정적 폴백/안내가 제공된다.
10. 승인된 부하/시험 조건에서 선택부터 재생 가능까지의 시간 분포를 계측하며, 60초 목표 달성 여부를 보고한다. 목표 미달이면 실패로 숨기지 않고 측정 결과를 남긴다.
11. 권한 없는 사용자가 타인의 task 상태나 자산에 접근할 수 없다.

## 13. 단계별 구현 계획

### Phase 0 — 계약 및 워크플로 확인

- `PROJECT_CONTEXT.md` 확보 및 실제 저장소의 `GET /current_region`, `POST /api/survey`, `GET /api/video-status/{task_id}` 코드/스키마 확인.
- 추천 로직의 후보 20개와 상위 5개 산출 필드·결정 규칙 확인.
- 장소별 LoRA 카탈로그/버전, `character.png` 경로·권리·처리 방법 확인.
- ComfyUI Cloud에서 단일 장소 end-to-end 워크플로를 실행해 노드/모델/입출력/실패/실제 지연 기록.

### Phase 1 — 추천 목록과 모의 작업

- 기존 지역/설문 계약을 연결하고 5개 카드 UI 및 상세-목록 복귀 흐름 구현.
- 실제 GPU 없이 task 상태 API와 완료 샘플 영상을 연결해 UI 상태 전이를 검증.
- 상태 계약, 권한 범위, 에러 표현 확정.

### Phase 2 — 단일 장소 생성 수직 슬라이스

- 백엔드 큐/워커, 장소-LoRA 매핑, ComfyUI Cloud 제출, 결과 저장·URL 발급 구현.
- 한 장소에서 이미지 생성 → 캐릭터 적용 → 약 10초 영상 생성 → 재생까지 연결.
- 로그·단계별 지연·재시도·실패/정적 폴백 구현.

### Phase 3 — 5개 장소 확장과 캐시

- 5개 카드별 독립 작업, 중복 제출 방지, 캐시, 큐 동시성/비용 상한 추가.
- 서로 다른 LoRA 매핑과 추천 세션 접근 제어 검증.
- 영상 재방문, URL 만료, 작업 만료/삭제 정책 반영.

### Phase 4 — 현장 검증 및 출시 판단

- 실제 네트워크·클라우드 부하에서 p50/p90/p95 및 60초 완료율 측정.
- 캐릭터 일관성, 장소 배경 연관성, 영상 품질, 재생 호환성에 대한 사람 평가.
- 운영 알림, 장애 대응, 개인정보·콘텐츠 정책 확인 후 제한된 MVP 공개.

## 15. 초기 권장 결정 요약

- 우선 사용자가 선택한 장소만 생성하고, 동일 세션 안에서 결과를 재사용한다.
- `GET /current_region`을 변경하지 않고 어댑터를 통해 기존 계약과 추천 세션을 연결한다.
- `POST /api/videos`를 작업 생성 경로로 제안하고 기존 상태 조회 경로를 보완한다.
- 비동기 큐 + 폴링으로 시작하며, 프론트엔드는 페이지 전환 후에도 task를 재조회한다.
- 정적 폴백은 영상 완료와 구별한다.
- 60초는 검증 전까지 목표로만 표시하고, 실제 ComfyUI Cloud 측정 결과로 조정한다.
